# How Personaxis works

A persona is the whole way a professional works: its procedures, criteria, tools, sourced knowledge,
what it has learned and the limits it keeps. Personaxis keeps that in plain files, compiles it into the
document an agent reads, and runs it through an engine that enforces its limits. The theorem-to-code
map is [`architecture/math-core.md`](./architecture/math-core.md); measured results are in
[`GUARANTEES.md`](./GUARANTEES.md).

## 2. The files of a persona

| File | What it is | How it changes |
|---|---|---|
| `personaxis.md` | The definition, in ten layers, with a declared range for every value that can move | Only through an edit the rules allow (`edit`, `decompile`, or a self-edit under its improvement policy) |
| `PERSONA.md` / `.claude/agents/<slug>.md` | The compiled document a model reads | Generated by `compile`; hand edits fold back with `decompile` |
| `record.jsonl` | The state: every value that moved, every turn, and who wrote each entry, hash-chained | Append-only |
| `state.json` | A view of the record: current values and the log of changes | Printed from the record; `state rebuild` checks it |
| `skills/`, `references/`, `personas/` | Its procedures, its sourced knowledge, its sub-personas | By hand, or from `create --research` and `skills pull` |

The ten layers are identity, character, personality, values and drives, affect, cognition, memory,
metacognition, self-regulation and persona. No one of them is the persona; together with the skills
and references they are.

## 3. What happens on a turn

`personaxis` with no subcommand opens the app. You talk in plain language, and each turn runs two
loops.

The agent loop does the work:

```
task → [ the model proposes a tool call → the gate decides (allow | ask | deny)
         → if ask, a person approves → it runs → its output is scanned ]*
       → finish
```

The built-in tools are `run_command`, `read_file`, `list_dir`, `find_in_files`, `write_file`,
`edit_file`, `check_page` and `finish`. A persona gets more only when it has what they reach: the
memory tools, `use_skill` for its skills, `run_service` for its services, `delegate` for its
sub-personas, `ask_person` when someone can answer, and `web_search` when a search key is configured.
The persona chooses its own skills: it reads each skill's one-line description and calls `use_skill`
when one fits.

The model only proposes a call. The gate decides, a denied call never runs, and every tool output is
scanned for prompt injection before it goes back to the model. `shift+tab` cycles the posture:
`read-only`, `workspace-write`, `danger-full-access`. Long conversations are compacted, by `/compact`
or automatically between turns, and `/resume` returns the compacted conversation.

The living loop keeps the persona's state:

```
observe   → the signal (input, tool output, reflection), with its source and an injection scan
appraise  → the model proposes structured signals only, never raw changes
evolve    → the engine applies the change clamped to the declared range, through the gate,
            and writes an entry to the record
recompile → only when a value crosses into another behavior band, which rewrites the compiled document
memory    → an entry in episodic memory, append-only and hash-chained
```

`improvement_policy.mode` decides how much of this applies:

- `locked`: nothing the persona lives through changes it. A persona with no mode declared is locked.
- `suggesting`: what `create` and `init` write. Changes to values apply inside their ranges; edits to
  the definition wait for a person to approve them.
- `autonomous`: edits apply directly, within the universal rules and the verifiers, and need a
  recorded sign-off (`approved_by`, `last_approval_at`).

## 4. What is enforced

- Every value stays inside its declared range, and a step can only move it so far (T1, T2). A value
  pushed away from its baseline leaves a minimum number of recorded entries (T3). The state replays
  from its record, and a tampered entry is located (T4, T5). With homeostasis on, values return toward
  their baseline (T6). Checked on 2,306,140 generated adversarial cases with 0 counterexamples.
- Twelve universal rules are enforced by the validator; a definition that breaks one does not compile.
  `validate` answers with five states and their exit codes.
- Memory is append-only, with the source of every entry and a hash chain. A deletion request is a
  tombstone, so the redaction itself is on the record. Each memory kind (episodic, semantic,
  procedural, autobiographical, user preferences, evaluations) is written only if the definition turns
  it on.
- The injection scanner normalizes Unicode, strips zero-width and bidirectional characters, folds
  homoglyphs and decodes base64 and hex before its rules run.
- Self-edits go through propose, apply and revert, with protected fields, a new version for each
  applied edit and a quorum of verifiers before it applies.
- Commands go through a policy on two axes, approval and sandbox, with a native wrapper where the OS
  has one (Seatbelt, bubblewrap).

## 5. How an agent loads a persona

1. Compiled file. `compile --platform claude-code | codex | openclaw | hermes` writes the document
   where that agent reads it. When a value crosses a band, the compiled document is rewritten.
2. MCP. `personaxis-mcp` serves 16 tools, among them `persona_compiled` (the document),
   `persona_state`, `adjust_persona_state`, `persona_observe`, `persona_audit`, `persona_propose_edit`,
   `scan_text`, `evaluate_command` and `skill_review`. The host brings the model; the server brings the
   persona and its rules.
3. ACP. `personaxis-acp` runs the persona as the agent inside an editor that speaks the Agent Client
   Protocol, and the gate's questions go to whoever is at that editor.
4. HTTP. `personaxis serve --persona <path>` serves the same operations and an `agents.md` for agents
   that speak neither.

A persona can also work on its own, without a host agent: the app runs the agent loop on any model you
configure.

## 6. The app

In a terminal, `personaxis` is a full-screen app with a `/` palette: `/persona`, `/status`, `/audit`,
`/memory`, `/doctor`, `/drift`, `/create`, `/compile`, `/skill`, `/model`, `/menu`, `/context`,
`/compact`, `/resume`, `/sandbox`, `/bg`, `/help`, `/exit`. Older command names say where their
function moved, and `/help moved` prints the map. In a pipe or CI it becomes a plain reader. Every view
also has a shell command with `--json`.

## 7. The repository

```
personaxis/                      one repository, eight packages released together
└── packages/
    ├── spec/      @personaxis/spec      schemas, validator, universal rules
    ├── core/      @personaxis/core      the engine: state, record, gate, memory, both loops, Genesis
    ├── protocol/  @personaxis/protocol  the transport between a front end and the engine, and ACP
    ├── cli/       personaxis            the app and the commands
    ├── mcp/       @personaxis/mcp       the MCP server
    ├── sdk/       @personaxis/sdk       run a persona inside your own backend
    ├── tui/       @personaxis/tui       terminal components and the dashboard
    └── evals/     @personaxis/evals     the conformance suite
```

The engine never prints. It emits events, and each front end (the app, MCP, HTTP, ACP) renders them,
so one engine serves every way a persona is loaded.

It installs from npm (`npm i -g personaxis`, Node 20.18.1 or newer), or as a single binary per platform
built with `pnpm run package`, with the schemas and templates embedded.

## 8. Run it from source

```bash
pnpm install && pnpm run build && pnpm run test
node packages/cli/dist/index.js                                            # the app
node packages/cli/dist/index.js serve --persona .personaxis/personaxis.md   # HTTP and agents.md
```

Point it at a model, local or hosted:

```bash
export PERSONAXIS_ENDPOINT=http://localhost:11434/v1
export PERSONAXIS_MODEL=qwen3:4b
```
